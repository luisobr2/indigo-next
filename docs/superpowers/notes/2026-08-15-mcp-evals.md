# MCP eval harness

`scripts/mcp-eval.mjs` is the only automated check on whether the MCP
server's read-only tools (`src/lib/mcp/tools.ts`) actually work, and the
only way to tell whether a later change to a tool or its description made
the agent-facing surface better or worse. It speaks raw JSON-RPC 2.0 over
HTTP directly against `POST /api/mcp` — no MCP SDK client, no LLM, no
agent — and every scenario asserts on the **parsed JSON a tool call
returns**, never on anything an agent says about it. The failure mode this
guards against is an agent claiming success while the underlying data is
wrong (or, worse, empty); a harness that "believes" the agent measures
nothing.

## Re-run it

```bash
MCP_URL=http://localhost:4000/api/mcp MCP_TOKEN='<login>.<apikey>' node scripts/mcp-eval.mjs
```

`MCP_URL` is the full `/api/mcp` endpoint of a running panel instance.
`MCP_TOKEN` is a real Odoo credential pair in `<login>.<apiKey>` form (an
Odoo user's login plus one of their API keys) — the same value a real MCP
client would send as `Authorization: Bearer <token>`. Both are required;
the script exits 1 immediately with a usage message if either is missing,
rather than hanging on a request that has nowhere to go or nothing to
authenticate with.

Exit code is 0 only if every scenario PASSed (SKIPs are allowed); non-zero
if anything FAILed.

## What each scenario proves

Two protocol-level checks run first, establishing that the endpoint speaks
MCP at all before any tool-specific assertion is attempted:

- **`initialize_ok`** — `POST` an `initialize` request; the response must
  be HTTP 2xx, parseable JSON-RPC, and carry a `result` (no top-level
  `error`). Proves the endpoint is up, authenticated, and MCP-compliant at
  the handshake level.
- **`tools_list_complete`** — `tools/list` must return a `result.tools`
  array containing all seven read-only tools: `today_board`, `find_orders`,
  `get_order`, `list_stages`, `list_dealers`, `list_designs`, and
  `list_people` (added later, once `assign_order`'s name-to-id gap became a
  real usability blocker — see the design spec's discovery-tools table).
  Proves no tool silently vanished from registration (e.g. a typo in
  `TOOL_DEFS` or a broken `server.registerTool` call).

Then the brief's nine scenarios, each calling one tool via `tools/call`
and asserting on the parsed `result.content[0].text` JSON:

- **`stages_are_ordered`** — `list_stages` returns at least 10 stages,
  every one has a non-empty `code`, and no two share a `code`. Guards the
  stage-filter contract every other order-filtering tool depends on
  (`find_orders`'s `stage` arg, the dealer pipeline).
- **`dealers_include_locktight`** — `list_dealers` contains a dealer whose
  `name` matches `/lock ?tight/i`. Lock Tight is a known seeded dealer
  (`data/demo_dealers.xml` / prod seed data per the project's `CLAUDE.md`)
  — its presence is a proxy for "the dealer catalog is really there," not
  an empty stub. Also stashes that dealer's `id` for
  `find_orders_by_dealer`.
- **`designs_are_grounded`** — `list_designs` returns at least 20 codes,
  and every `code` matches `/^[A-Z0-9][A-Z0-9_-]*$/`. Guards against a
  tool that returns garbage or truncated codes an agent would then quote
  back to a user as if they were real catalog entries.
- **`today_board_shape`** — `today_board` returns
  `{ stages: [{ stage, code, orders: [...] }, ...] }` (an array of
  per-stage groups), and every group's `orders` is an array. **Deviation
  from the brief's one-line description**, noted deliberately: the brief
  describes this as "an object keyed by stage, every value an array,"
  which reads as `{ "Painting": [...], "CNC": [...] }`. The tool's actual
  implementation (`todayBoard()` in `src/lib/mcp/tools.ts`) returns
  `{ stages: [...] }` — an array of `{stage, code, orders}` groups, not a
  plain object keyed by stage name. The assertion here checks the real
  shape, verified field-by-field against `tools.ts`, and this note
  documents the deviation rather than silently reconciling it. This is
  not a bug in the tool — just an informal table description that doesn't
  match the code precisely.
- **`find_orders_by_dealer`** — `find_orders` filtered to the Lock Tight
  dealer's rows, asserting every returned row's `dealer` field matches
  `/lock ?tight/i`. **Also a deliberate interpretation, not a literal
  reading**: the brief says "find_orders with the dealer name from
  scenario 2," but `find_orders`'s own `inputSchema` (in `tools.ts`) says
  its free-text `q` argument matches order number, client name, or
  `dealer_ref` (a per-order reference string) — **not** the dealer's
  display name. Passing the dealer's name as `q` would test an
  unsupported combination that the schema doesn't promise to work. This
  scenario instead uses the numeric `dealer_id` argument, exactly as the
  tool's own description instructs ("Get it from list_dealers — do not
  guess one"). If this environment has zero orders for that dealer, the
  scenario **SKIPs** with a clear reason instead of either failing (too
  strict for a legitimately sparse dev DB) or silently passing on an
  empty array (which would defeat the point of the assertion — see below).
- **`get_order_roundtrip`** — takes the order id found by
  `find_orders_by_dealer` and calls `get_order` on it, asserting the
  returned `id` matches and `lines` is an array. If
  `find_orders_by_dealer` SKIPped (no Lock Tight orders here), this
  scenario falls back to an unfiltered `find_orders` call so `get_order`
  still gets exercised against *some* order — only SKIPping outright if
  the environment has zero orders at all. This fallback is a deliberate
  robustness choice beyond the brief's literal chaining, made so a sparse
  dealer bucket doesn't also blind this scenario to a genuinely broken
  `get_order`.
- **`limit_is_capped`** — `find_orders` called with `limit: 5000` returns
  at most 100 rows. Proves the blast-radius cap in `clampLimit()`
  (`MAX_LIMIT = 100` in `tools.ts`) actually holds server-side and can't
  be overridden by the caller.
- **`unknown_tool_is_an_error`** — `tools/call` with
  `name: "definitely_not_a_tool"` gets back a well-formed JSON-RPC
  message that signals failure, not a crash or a hang. Accepts either a
  top-level JSON-RPC `error` or a tool result with `isError: true`,
  because both are valid per the MCP spec and per the installed SDK
  (`@modelcontextprotocol/server`): calling an unregistered tool name
  never reaches `runTool`'s own `try/catch` (which only guards *registered*
  tools failing at runtime) — it's rejected earlier, inside the SDK's own
  request dispatch, as a protocol-level `ProtocolError` (confirmed by
  reading `node_modules/@modelcontextprotocol/server/dist/mcp-*.mjs`,
  which throws `Tool ${name} not found` before any handler runs). That
  becomes a top-level JSON-RPC error in this SDK version, but the
  assertion accepts either shape so it isn't coupled to that internal
  detail.
- **`bad_token_is_401`** — a request with an obviously bogus bearer token
  (`not-a-real-login.not-a-real-apikey`) gets back HTTP 401. Confirms
  `verifyMcpToken` genuinely rejects bad credentials rather than
  defaulting open.

## Design notes

- **SKIP vs FAIL vs PASS are distinguished in the totals line**, and a
  SKIP is never silent — every SKIP prints a one-line reason (e.g. "no
  orders exist in this environment at all"). Only `find_orders_by_dealer`
  and `get_order_roundtrip` can SKIP; every other scenario is a hard
  PASS/FAIL, because catalog data (stages, dealers, designs) is expected
  to exist in any environment this runs against, per the project's own
  seed data, while order volume for one specific dealer is not.
- **The "returns an empty array for everything" regression is caught**:
  `stages_are_ordered` (≥10), `dealers_include_locktight` (a specific
  name must be present), and `designs_are_grounded` (≥20) all fail hard
  on an empty or near-empty result — they don't merely check "is this an
  array." This was verified directly: a throwaway mock MCP server was
  stood up locally (not the real Indigo panel) that returns `[]`/`null`
  from every tool, and running the harness against it produced exactly
  the expected 3 FAILs, 2 SKIPs, 6 PASSes — confirming the harness
  actually distinguishes a broken server from a healthy one rather than
  passing regardless of the data.
- **Both JSON and SSE response shapes are handled.** `postRpc()` checks
  the response `Content-Type`: `application/json` is parsed directly,
  `text/event-stream` is parsed line-by-line for `data:` frames. This was
  also verified against a mock server forced to answer over SSE for every
  request — same 11/11 PASS result as the plain-JSON mock, confirming the
  SSE branch is not dead code. In this project's actual deployment
  (`@modelcontextprotocol/server`'s `createMcpHandler`, read in
  `node_modules/@modelcontextprotocol/server/dist/index.mjs`), responses
  are always plain JSON — the SSE path exists for spec-compliance with
  other streamable-HTTP servers, per the task's explicit "handle both;
  do not assume" instruction.
- **`Mcp-Session-Id` is echoed if the server ever sends one.** Verified by
  reading the SDK source that this deployment's specific transport
  (`PerRequestHTTPServerTransport`, a single-exchange-per-request design)
  never actually issues one — each HTTP call is independently a complete
  request/response cycle, so there is no session to maintain. The harness
  still captures and echoes the header defensively in case that changes
  or a differently-configured MCP server is pointed at this same script.
- **Every FAIL prints expected vs. actual**, truncated to ~500 characters,
  so a failure is diagnosable from the console output alone without
  re-running anything by hand.

## Real run output

Run on 2026-08-15 against a locally-built panel (standalone server, port 4100)
pointed at **production Odoo** (`indigo-prod`), authenticating with a real API
key minted for `ics-service@indigodecors.com`. Read-only throughout.

```
MCP eval harness — target http://127.0.0.1:4100/api/mcp

PASS initialize_ok
PASS tools_list_complete
PASS stages_are_ordered
PASS dealers_include_locktight
PASS designs_are_grounded
PASS today_board_shape
PASS find_orders_by_dealer
PASS get_order_roundtrip
PASS limit_is_capped
PASS unknown_tool_is_an_error
PASS bad_token_is_401

Totals: 11 passed, 0 failed, 0 skipped (of 11 scenarios)
```

Independently observed in the same session, outside the harness:

- `tools/list` returned exactly the six expected tools.
- `list_stages` returned the 13 real pipeline stages, starting `new`,
  `design_pending`, `design_confirmed` — i.e. the tools reach real data, not a
  fixture.
- The endpoint answered **401** both with no `Authorization` header and with a
  bogus bearer.
- An `indigo.design` `create` attempted directly over the same credential pair
  was **refused by Odoo**. The read-only property of this phase is therefore
  enforced by Odoo's ACL on the calling user, not merely by which tools we chose
  to expose — the stronger of the two guarantees.

  **Correction (2026-08-15, later the same day):** this was tested with only
  one account, `ics-service@indigodecors.com` — an **office**-role account —
  and the "stronger of the two guarantees" framing above was wrongly
  generalised to every MCP credential. It doesn't hold for a **manager**
  identity: `check_access_rights("create")` on `indigo.design` returns `True`
  for a manager account (verified directly against staging with four real
  accounts, including a manager). Manager identities — which includes
  Majela, the primary operator of this whole MCP surface — get NO backstop
  from Odoo's ACL on this operation; for them, the tool surface this project
  chooses to expose is the only boundary. Full measurement, table, and the
  decision made about it: `docs/superpowers/notes/2026-08-15-mcp-acl-boundary.md`.
  `scripts/mcp-eval.mjs`'s `write_is_refused` scenario has been corrected to
  match — it now checks the caller's own role before asserting refusal.

### What this run did NOT prove

No agent was involved. The harness speaks raw JSON-RPC, so it verifies the
server and its data, not whether a model picks the right tool from a Spanish
sentence. That is the next measurement, and it needs a different harness.
