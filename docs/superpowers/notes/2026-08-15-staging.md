# Entorno de staging

Existe desde 2026-08-15. Es el único lugar donde un agente con escritura puede
equivocarse sin consecuencias, y por eso el spec lo llama precondición y no lujo.

## Qué es

Un **segundo Odoo** en el mismo VPS, contra una **copia saneada** de la base de
producción. No hay un panel de staging desplegado: el panel se corre local y se
apunta ahí.

| | |
|---|---|
| Contenedor | `indigo-odoo-staging` (imagen `indigo-odoo:17-custom`, la misma de prod) |
| Base | `indigo-staging`, en el **mismo** Postgres que producción |
| Puerto | `127.0.0.1:8169` en el VPS — **no expuesto a internet**, a propósito |
| Filtro | `--db-filter='^indigo-staging$'` — no puede servir `indigo-prod` ni por error |
| Datos | 231 órdenes, 163 diseños, 26 usuarios, filestore de 138 MB |

## Por qué es seguro

Antes de encenderlo se le sacaron los dientes. Un Odoo de staging con la config
de producción **le manda correo real a los clientes y a los managers**, y crear
una orden dispara un aviso inmediato — habría sido el primer daño real.

| | staging | prod |
|---|---|---|
| `ir.mail_server` | **0** | 1 |
| Crons activos | **0** | 20 |
| Correo en cola | 0 (cancelado) | — |
| Nombre de la empresa | `Indigo Publicity Corp. [STAGING]` | sin sufijo |
| PII de clientes | anonimizada | real |

La anonimización cubre nombres, emails, teléfonos y direcciones de los 231
pedidos y de 55 partners. **El staff conserva su identidad** a propósito: los
roles y las record rules se prueban con los usuarios reales, que es lo que hace
que la prueba valga.

## Cómo llegar

Está atado a localhost del VPS, así que hace falta un túnel:

```bash
ssh -N -L 8169:127.0.0.1:8169 root@2.25.137.220
```

Con el túnel abierto, `http://127.0.0.1:8169` es el Odoo de staging desde tu
máquina.

### Correr el panel contra staging

```bash
ODOO_URL=http://127.0.0.1:8169 ODOO_DB=indigo-staging npm run dev
```

O poné eso en `.env.local`. **Ese archivo apunta a producción por defecto** —
es el hueco que este entorno viene a tapar. Para cualquier trabajo que escriba,
cambialo.

### Correr las evals del MCP contra staging

```bash
MCP_URL=http://localhost:4000/api/mcp \
MCP_TOKEN='<login>.<apikey>' \
ODOO_URL=http://127.0.0.1:8169 ODOO_DB=indigo-staging \
node scripts/mcp-eval.mjs
```

Las API keys de producción **funcionan en staging**: el clon copió la tabla
`res.users.apikeys`. Cómodo, pero implica que revocar una clave hay que hacerlo
en las dos bases — está contemplado en el procedimiento de rotación.

## Operación

- **Reiniciar**: `docker restart indigo-odoo-staging`
- **Logs**: `docker logs -f indigo-odoo-staging`
- **Refrescar los datos desde producción**: volver a clonar y volver a sanear.
  El saneo **no es opcional** — un clon crudo tiene los mail servers y los crons
  de producción vivos.
- **Apagarlo**: `docker rm -f indigo-odoo-staging`. La base sobrevive.

## Lo que este staging todavía no es

- **No hay panel desplegado.** El panel se corre local. Si en algún momento se
  quiere un `staging.indigodecors.com`, hay que crear el recurso en Coolify y un
  registro DNS.
- **Comparte el Postgres con producción.** Aislar las bases es suficiente para
  el uso previsto, pero no protege contra un error a nivel servidor. Si alguna
  vez se prueba algo que toque el motor y no solo los datos, hace falta un
  Postgres aparte.
- **Los datos envejecen.** Es una foto del 2026-08-15; no se sincroniza sola.
